# Brute v0.24.0 plan: BRUTE_PLAN_027 (BRUTE-0240-SCALE-REPLAY-027)

Status: **pre-registered, plan only.** No build is authorized, no code is written, no data exists. Canonical file: `experiments/BRUTE_PLAN_027.json`.

- **Question.** Does the frozen S2 exact search (brute.certify/12, method s2, unchanged from v0.23.0) meet the GSC clauses on a full, uninterrupted 93-case run on fresh seeds?
- **Why.** v0.23.0 decided nothing: a host reboot stopped the run after 38 of 93 cases, and no scale8 or control case was reached (deviation #125). On the 38 sealed cases (descriptive only), S2 finished exact on 0 of 24 scale16 cases, its unknown fraction U was 0.566, it issued 0 certificates, and the smoke showed S2 slower than S1 at 12-16 states. Clause c is unlikely to pass. v0.24.0 publishes the result either way.
- **Design.** Same worlds, arms, horizon (176), budgets (120 s per case, 10 s per query, 8 workers, 1800 s cap), criteria a-e, G10, GAPI12, GS_ref12 and G_recount as BRUTE_PLAN_026. The S2 code and the 026 scoring scripts are reused byte-identical; only the new items below differ.
- **Seeds.** scale8 9310001-12, scale12 9320001-12, scale16 9330001-12, control 9340001-6. The 93 cases are declared in advance.
- **New 1: job order.** Cases are dispatched in the order control_cycle3, scale8, stress, scale12, scale16. The gates that need the small worlds (G10, GS_ref12, clauses b and e) then get their data first. 026 dispatched scale16 first.
- **New 2: durable checkpoint.** After each case finishes, the runner appends to CHECKPOINT.jsonl and calls fsync. A host-side watcher, separate from the core API, commits and pushes a gzip snapshot of CHECKPOINT to plan/v0.24.0 every 5 minutes, so a disk revert loses at most 5 minutes of cases.
- **New 3: interruption policy.** PROPOSED, NEEDS OWNER APPROVAL. It would change the standing rule 'never relaunch a live run'. A host interruption is defined as follows: the runner process is gone, no timeout fired, and uptime shows a reboot. On such an interruption the run may resume at most once. The resume is ledgered first (event resume_027) and skips the job keys in the last pushed snapshot. G_RT counts the summed active run segments against 1800 s. Without owner approval the 026 rule stands: seal partial, every data gate FAILS (INCOMPLETE_INPUT), and nothing is relaunched.
- **New 4: S2_tight, informational only.** S2_tight: S2 with n_max set to the family's true state count, so that n_max = n. It is reported only, not gated, and tests whether certificates are about 0 because n_max is larger than n (a smoke finding).
- **Run time.** Inferred from the 026 partial run: mean case wall 121.9 s, 93 cases over 8 workers, about 1420-1500 s against the 1800 s cap. The margin is thin. If the seedcheck-time smoke projects more than 1700 s, the stress cases are the first to be cut, and only by a ledgered amendment before any held-out data.
- **Failure.** Any clause or gate that does not pass, including an INCOMPLETE_INPUT after an interruption. It is published as it stands.
